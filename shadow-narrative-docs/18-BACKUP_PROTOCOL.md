# Shadow Narrative — Backup Protocol

> **状态：只写协议，不实现后端。**
> 本文档定义客户端与备份后端之间的约定。后端代码在真要用时再写。
> 本机现有的 PostgreSQL 可作为开发期的后端替身。

## 1. 目标与非目标

### 目标

- 把本地数据**增量**备份到用户自己的后端
- 照片天然去重：同一张照片传一次
- 恢复时能完整重建：照片、文字、对话、日志一个不少

### 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| **双向同步** | 需要墓碑、版本向量、冲突策略。工作量是备份的 3–5 倍，做错就丢数据 |
| **多设备并发写** | 后写的覆盖先写的。真要多设备同时用，是另一个产品问题 |
| **服务端解析** | 后端是哑存储，不理解"照片""对话"是什么 —— 端到端加密后它还**读不到**（§11），连 `counts` 都看不见 |
| **服务端 AI** | AI 只在本机算（`17-SELF_HOSTING.md` §4） |
| **服务端持有密钥** | 端到端加密的先决条件。有代管密钥就不是端到端（§11） |

## 2. 核心设计

### 不复用同一套 schema

本地是 SQLite，后端是 PostgreSQL。**两边不共享表结构。**

如果按"同样的表往 Postgres 里写"，就要维护两套 schema 的同步 ——
每加一个字段都要改两处、写两次迁移、还要处理类型差异（SQLite 没有 enum、
JSON 支持不同）。这个代价会一直复利。

### 内容寻址 blob + 快照清单

```text
photo 文件本身    →  加密后按【密钥化哈希】寻址的 blob
其余一切结构化数据 →  一份加密的 JSON 快照清单
```

| 好处 | 说明 |
|---|---|
| 照片天然去重 | 同一张照片重复备份只传一次；本地重复文件也自动合并 |
| 增量几乎免费 | 新增 N 张照片 = 传 N 个 blob，其余全部 HEAD 命中 |
| 后端极简 | 一张 blob 表 + 一张快照表，不需要理解业务，**也读不到内容** |
| 恢复可校验 | 每个 blob 解密后校验哈希，传输损坏能被发现 |

关于「密钥化哈希」与端到端加密的关系，见 §11 —— 那一节是本节的前提，
不读它会把 blob key 设计错。

## 3. 数据格式

### Blob

```
key    <blobId>           = HMAC-SHA256(用户密钥, sha256(明文))，64 位小写十六进制
value  加密后的文件字节     （随机 IV，见 §11）
```

`blobId` 是**密钥化**的，不是明文哈希 —— 理由见 §11，那是本节的关键。
它仍然满足内容寻址要的两条：
- 同一张照片在本地被删除又重新导入，不会重复占用后端空间
- 恢复时不需要知道原来的 id 是什么

但**后端无法用它验证自己收到的是什么**（它没有密钥）。完整性校验因此移到客户端 ——
见 §5。

### 快照清单

一份自包含的 JSON，包含**全部结构化数据**（照片文件除外，它们走 blob）。

```json
{
  "protocol": 1,
  "snapshotId": "sn_01J...",
  "createdAt": "2026-10-09T08:00:00.000Z",
  "deviceId": "dev_a1b2c3",
  "appVersion": "0.4.0",

  "counts": {
    "photos": 42,
    "memories": 5,
    "memoryPhotos": 61,
    "analyses": 42,
    "conversations": 42,
    "messages": 310,
    "journals": 8
  },

  "records": {
    "photos":       [ { "id": "...", "contentHash": "sha256:...", "...": "..." } ],
    "memories":     [ ... ],
    "memoryPhotos": [ ... ],
    "analyses":     [ ... ],
    "conversations":[ ... ],
    "messages":     [ ... ],
    "journals":     [ ... ]
  },

  "blobs": [ "sha256:...", "sha256:..." ]
}
```

**上传前整体加密**（§11）。后端拿到的是密文，看不到下面这些字段里的任何一个 ——
包括 `counts`。

字段与 `08-DATA_API_SPEC.md` §3 的 schema 一一对应，**键名一致**，
恢复时不需要映射表。

> ⚠️ **待定：分组键名**。上面示例里的 `analyses` / `messages` 与 Prisma 模型名
> （`PhotoAnalysis` / `ConversationMessage`）不一致。「键名一致」这条要求的是
> **字段级**一致（那些已经对齐）；分组键用哪一套，落地 Round 11 时以本节示例为准，
> 不要在各处临时决定。

`deviceId` 用于区分不同机器的快照，但**不做冲突合并** —— 见 §4。

## 4. 冲突与覆盖语义

备份是**单向**的：本地是唯一可写的，云端只读。

所以：

- 同一 `deviceId` 的连续快照是**取代关系**，最新的代表当前完整状态
- 不同 `deviceId` 的快照**互不合并**。两个设备各自备份，恢复时由用户选择用哪一份
- **没有"自动合并"这回事。** 说有就是骗人

## 5. 接口

```text
HEAD   /api/backup/blobs/:blobId          存在性检查（跳过重复上传）
POST   /api/backup/blobs/:blobId          上传单个 blob（幂等）
GET    /api/backup/blobs/:blobId          下载

PUT    /api/backup/snapshots/:id        上传快照清单
GET    /api/backup/snapshots            列出快照（不含 records）
GET    /api/backup/snapshots/:id        下载快照清单
DELETE /api/backup/snapshots/:id        删除快照（**不动 blob**）
```

### `:blobId` 的格式与校验

64 位小写十六进制（`HMAC-SHA256` 的输出）。

服务端能校验的只有**格式**，以及幂等语义：

- 格式不合法 → 拒绝
- `POST` 一个已存在的 `blobId` → 当作成功，**不覆盖已存的字节**

**服务端无法校验内容。** 它没有密钥，收到的就是密文；而且同一张照片每次加密
（随机 IV）密文都不同，所以「重传同一张会不会覆盖成不同字节」这件事只能靠
「已存在就跳过」来保证，不能靠比对内容。

因此**完整性校验由客户端负责**：下载后解密、算 `sha256(明文)`、比对本地记录。
这一条在 §9 的恢复流程里是强制的，不是可选的。

原文这里写的是「服务端必须校验收到的字节的哈希与路径一致」。端到端加密之后
这条**物理上做不到**了 —— 不是放松要求，是校验责任转移到了唯一持有密钥的一方。

### 删除语义

删快照**不删 blob**。因为一个 blob 可能被多个快照引用，而且 blob 是内容寻址的，
没有引用计数的话删除会导致其他快照不可恢复。

清理孤立 blob 由后端**定期垃圾回收**（扫描所有快照的 `blobs` 并集，
删掉不在并集里的），不在协议里做实时引用计数。

## 6. 本地状态

`<数据目录>/backup-state.json`：

```json
{
  "endpoint": "https://backup.example.com",
  "deviceId": "dev_a1b2c3",
  "lastSnapshotId": "sn_01J...",
  "lastBackupAt": "2026-10-09T08:00:00.000Z",
  "lastResult": "ok",
  "uploadedHashes": ["sha256:...", "..."]
}
```

`uploadedHashes` 是**本地缓存**，只用来少发几个 HEAD 请求。
它丢了不影响正确性 —— 服务端的 HEAD 才是权威。

## 7. 认证

- 用户在设置页填入**后端地址**和**访问令牌**
- 请求头：`Authorization: Bearer <token>`
- 令牌存 `secrets.json`（`17-SELF_HOSTING.md` §3），**不进数据库、不进日志**

> 令牌**不写进数据库**。`08-DATA_API_SPEC.md` §3 早期版本的 `UserSettings.backupToken`
> 已删除：它既是凭据不该持久化在业务表里，而且快照清单（§3）会把整行记录带走 ——
> 那等于**把备份令牌备份到备份后端上**。凭据一律只存 `secrets.json`。

**端到端加密密钥也存这里**（§11）。它和访问令牌是两回事：
令牌是"后端允许我上传"，密钥是"只有我能读回内容"。丢了令牌重新签发即可，
丢了密钥就永久读不回来了。

后端如何签发令牌不在本协议范围内 —— 那是后端自己的账号体系。

## 8. 备份流程

```text
1. 检查 endpoint 与 token 是否配置，没有就中止并提示

2. 收集全部 photo.contentHash

3. 逐个 blob：
     HEAD /api/backup/blobs/:hash
       204 → 已存在，跳过
       404 → POST 上传
   上传失败 → 记录，继续下一个（不要因为一张照片失败就放弃整次备份）

4. 生成快照清单（含本次全部 records 与 blobs 列表）

5. PUT /api/backup/snapshots/:id

6. 更新 backup-state.json
```

### 第三步的顺序

**先传 blob，最后传快照。** 反过来的话，快照会引用还不存在的 blob，
恢复时才发现缺文件 —— 那时候备份已经被当成成功的了。

## 9. 恢复流程

```text
1. GET /api/backup/snapshots  列出快照，用户选一个

2. GET /api/backup/snapshots/:id  下载清单

3. 对比本地与清单里的 blobs，缺哪些就下载哪些
     **下载后必须校验**：解密 → 算 sha256(明文) → 比对，不符则重试。
     这一步在端到端加密下是强制的，不是可选的 —— 服务端没有密钥，
     它无法替你验证任何内容（§5）

4. 导入数据库（按 id upsert）
```

### 恢复默认导入到新目录

**不覆盖当前数据。** 恢复时要求用户指定一个空的数据目录，导入完成后
启动时选择用哪个目录。

理由：备份是单向的，恢复是破坏性的。让"恢复"顺手覆盖掉当前库，
是那种一旦点错就无法挽回的操作。

### 恢复需要重建的字段

清单里存的是 `storageKey`（照片在本地磁盘上的文件名），恢复时**保持原样**，
因为 blob 按内容哈希去重、文件名只是本地引用，保持原样最简单也最不容易错。

## 10. 失败与重试

| 情况 | 处理 |
|---|---|
| 网络中断 | 整个备份可重入。已上传的 blob 靠 HEAD 跳过 |
| 单个 blob 上传失败 | 记录并继续，最后统一报"部分完成" |
| 快照上传失败 | 视为整次备份失败（它是原子性的一步） |
| 令牌失效 | 提示用户重新配置，不自动重试 |

**不做断点续传的分块上传。** 单张照片最大 25MB（`08-DATA_API_SPEC.md` §12），
一次性 POST 足够。真要传几百 MB 的文件时再说。

## 11. 隐私边界（必须说清楚）

**备份做端到端加密。后端读不到任何内容。**

> 本节于 2026-10-09 **反转**。原文是「备份不做端到端加密，后端能读到全部内容」，
> 那是自托管单用户形态下的决定（后端管理员就是用户自己）。
> 产品方向确认为**多用户 + 同步到同一个后端存储**之后，这个前提不成立了：
> 后端管理员会变成"能看到所有用户的照片和全部文字的人"。所以改为端到端加密。

### 加密范围

| 内容 | 处理 |
|---|---|
| 照片文件（blob） | 用用户密钥加密后上传。后端只存密文 |
| 快照清单（§3 的全部结构化数据） | 整体加密后上传 |

后端因此**连 `counts` 都读不到** —— 它不知道这个用户有几张照片、几段对话。
这是刻意的：`counts` 本身也是隐私（照片数量、对话数量能推断出相当多东西）。

### blob key 必须是密钥化哈希

§2 的 `key = sha256(明文)` **在加密之后不再可用**：

- 密文每张都不同（随机 IV），`sha256(密文)` 各不相同 → 去重彻底失效，同一张照片每次备份都要重传
- 但把**明文哈希原样当 key 上传**同样不行 —— 服务端拿到 `sha256(明文)` 就是一个**确认预言机**：
  它可以拿一张已知照片算哈希，去暴力比对「这个用户是不是有这张照片」

所以分两层：

```text
本地：contentHash = sha256(明文)                        身份 / 完整性 / 本地去重
上行：blobId      = HMAC-SHA256(用户密钥, contentHash)   服务端 blob 主键
```

同一张照片 → 同一个 blobId → 服务端已存在就跳过；去重回来了，
而服务端拿到的 id 是密钥化的，比对不出任何已知内容。

`Photo.contentHash`（`08-DATA_API_SPEC.md` §3）存的是**前者**，
blobId 的推导属于客户端实现，不入库。

### 密钥

- 密钥是**用户自己的**，存 `<数据目录>/secrets.json`（`17-SELF_HOSTING.md` §3 §4）
- 后端永远拿不到它。没有「平台代管密钥」这回事 —— 有的话就不是端到端
- 用户必须能导出密钥（换机器、重装系统）

### 代价：丢了密钥就永远找不回来

**没有密码重置。** 密钥丢了，后端上的备份就是一堆读不出来的字节 ——
不是"打不开"，是**永久无法恢复**。

界面上必须在两处把这句话写出来，不能只写在文档里：

1. 开启备份的地方
2. 导出/显示密钥的地方

### 端到端保护不了什么

**它保护的是「后端管理员」，不保护「模型服务商」。**

`autoAnalyze` 开启时，照片仍然以**明文**发给 DeepSeek —— AI 只在本机算（§1），
但"在本机算"不等于"没有离开这台机器"。照片确实去了第三方模型服务商。

这是两个独立的隐私面，界面上要分开讲清楚（`12-SECURITY_PRIVACY.md` §5）：
不要让人因为"备份是加密的"就以为照片没有离开过机器。

## 12. 触发方式

| 方式 | 说明 |
|---|---|
| **手动** | 默认。设置页或左下角一个低存在感的入口 |
| **自动** | 可选开启。上传/删除后把变更排进队列，空闲时上传 |

自动模式必须：
- 在界面上有可见的状态（进行中 / 上次成功时间 / 失败）
- 失败时不静默重试到天荒地老，要能停下来并告诉用户
