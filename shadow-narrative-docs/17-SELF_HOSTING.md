# Shadow Narrative — Self-Hosting

本文档定义 Shadow Narrative 交付给最终用户的形态。

## 1. 形态

> **⚠️ 2026-10-10：本节已过时，交付形态正在改变。**
>
> 用户定的是**独立的桌面 app**（双击图标就开），不是「起个服务、用浏览器打开」。
> 改写属于 `10-IMPLEMENTATION_PLAN.md` 的 **Round 13**，
> 但技术前提已经实测通过（standalone 产物起得来、原生模块能追踪）。
>
> **下面描述的进程形态仍然准确** —— Electron 的方案就是把这些包进一个
> 原生窗口里（主进程把服务器当子进程起）。变的只是「怎么打开它」，
> 以及打包后数据目录要落到系统的应用数据目录。
>
> 在 Round 13 动手之前，本节按现状读；动手时必须重写。

**一个跑在用户自己机器上的 Node 服务，用浏览器访问。**

```text
用户机器
├── Node 服务（Next.js，本地端口）
│   └── http://localhost:3000
├── 数据目录
│   ├── shadow-narrative.db       SQLite
│   └── photos/                   照片文件
└── 浏览器（访问 localhost）
```

用户不需要装数据库服务、不需要 Docker、不需要账号。

## 2. 为什么是自托管

| 原因 | 说明 |
|---|---|
| **隐私** | 照片和文字全程不出这台机器 |
| **零成本** | 没有服务器账单，没有账号体系要维护 |
| **零配置** | SQLite 一个文件，没有要装要配要常驻的数据库服务 |

### 代价（必须承认）

| 代价 | 缓解 |
|---|---|
| 用户要装 Node | `17 §5` 的首次运行流程压到三步；以后可加 Docker 镜像 |
| 跨设备不方便 | 靠**备份 + 恢复**（`18-BACKUP_PROTOCOL.md`），不做实时同步 |
| 没有自动更新 | 手动拉新版本、跑迁移 |
| AI 需要用户自己的 key | 这是必然的 —— 见 §4 |

## 3. 数据目录

```text
<数据目录>/
├── shadow-narrative.db       SQLite 主库
├── photos/                   原图与缩略图
│   ├── <uuid>.<ext>
│   └── <uuid>.thumb.<ext>    缩略图（08 §6），与它那张原图同 stem
├── backup-state.json         备份游标与远程映射（见 18 §6）
└── secrets.json              AI key / 备份令牌 / 端到端加密密钥（0600 权限）
```

缩略图和原图**放同一个目录**，不另开子目录：`08 §16` 的删除本来就是按
storage key 逐个删的，同目录不改变任何逻辑。`.thumb.` 只是让 `ls` 时
一眼看得出归属。

**缩略图不进备份**（`18 §2`）—— 它是可从原图重新生成的派生资源。

### 位置

| 场景 | 路径 |
|---|---|
| 开发 | 项目根目录下的 `.data/` |
| 自托管运行 | 由环境变量 `SN_DATA_DIR` 指定，默认 `<用户主目录>/.shadow-narrative/` |

**整个目录可以整体打包搬走** —— 这是最朴素也最可靠的迁移与备份方式，
不依赖任何协议。`18-BACKUP_PROTOCOL.md` 解决的是"增量上云"，不是"换机器"。

### 权限

`secrets.json` 必须只在用户可读（Unix `0600`）。Windows 上依赖用户目录的默认 ACL。

## 4. AI 凭据

**每个用户用自己的 DeepSeek API key。**

这在本架构下是必然的：
- 服务端就是用户的机器，不存在"平台替你付钱"的模式
- 也没有中间方能看到你的 key

配置入口：设置卡 → AI → 填入 key。存进 `secrets.json`，不进数据库、不进日志。

> 与 `12-SECURITY_PRIVACY.md` §10 一致：日志不得记录 key。

### ⚠️ 2026-10-10：环境变量那条回退删了

原先 `secrets.json` 的非空值优先、其次读 `AI_API_KEY` / `AI_BASE_URL` /
`AI_MODEL` 三个环境变量。用户的原话是「**apikey 那里不提供默认的，
说一下存在哪就行**」—— 现在**只有一个来源**：`secrets.json`。

删它的理由不是「多一条路不好」，而是**那条路让设置卡说不出真话**：
key 可以从两个地方来，卡片就得回答三个问题 —— 配没配、是不是来自环境变量、
点「清除」为什么没用 —— 而没有一个问题与用户要做的事有关。

设置卡现在只回答一件事：**配好了没有**，外加一句「存在数据目录里的
secrets.json」。

⚠️ 那里**不显示绝对路径**。用户 2026-10-10 补了一句：「那个路径显示相对路径吧，
**后面封装成 app**」—— `F:\...\.data\secrets.json` 是这台机器的实现细节，
封装成桌面 app 之后那个前缀就不成立了（数据目录会变成
`app.getPath('userData')`，见 `10` 的 Round 13）。`SettingsView` 里一度加过的
`secretsPath` 也随之删掉，服务端不再回传路径。

将来封装时若要做「打开数据目录」，**那是一个按钮，不是一段路径文本**。

`.env.example` 里那一节换成了说明，不再列变量。

⚠️ **对已经这么配的人来说这是破坏性的**：`.env.local` 里的 `AI_API_KEY`
不再生效，要在设置卡里粘一次。`secrets.json` 长这样，后两项可省略
（省略就用上面那两个默认值）：

```json
{
  "aiApiKey": "<key>",
  "aiBaseUrl": "https://api.deepseek.com",
  "aiModel": "deepseek-flash"
}
```

要换厂商或自跑模型，改 `aiBaseUrl` / `aiModel` 即可（`05 §7`）——
那条路一直存在，只是入口从环境变量收成了这一个。

## 5. 首次运行

```bash
git clone <repo>
cd shadow-narrative
npm install
npm run setup      # 建数据目录、跑迁移、生成初始配置
npm start
```

然后浏览器打开 `http://localhost:3000`。

`npm run setup` 需要做的事：

```text
1. 解析 SN_DATA_DIR（未设置则用默认位置）
2. 创建目录结构
3. 执行 prisma migrate deploy
4. 若无 secrets.json，生成模板
5. 打印数据目录位置与访问地址
```

## 6. 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `SN_DATA_DIR` | `~/.shadow-narrative` | 数据目录 |
| `PORT` | `3000` | 监听端口 |
| `SN_HOST` | `127.0.0.1` | 监听地址 |
| `SN_BACKUP_ENDPOINT` | 空 | 备份后端地址，不填则禁用备份 |
| `NODE_ENV` | `production` | — |

### 关于 `SN_HOST`

**默认只监听 `127.0.0.1`。** 改成 `0.0.0.0` 等于把整个照片库暴露在局域网上，
而本产品**没有任何鉴权**（单用户自托管，登录只用于备份）。

文档和界面都不主动引导用户去改它。真要局域网访问，那是用户自己的决定，
必须自己承担风险。

> ⚠️ **2026-10-10：本节原先还要求「设置页里要把这句话写出来」，删掉了。**
>
> 设置面板上**没有任何东西能改 `SN_HOST`** —— 它是这里的一个环境变量。
> 用户的原话是「硬性要求和界面无关、写这些干啥」。摆在面板里它只是一段
> 谁也动不了的告示；而真去改 `0.0.0.0` 的人一定在改环境变量，也就一定会
> 读到本节。
>
> **这句话的读者是改配置的人，不是打开设置的人。** 本节从今往后是它
> **唯一**的落点，不要再往界面上加回去。

## 7. 数据库迁移

用 Prisma migrate。

```bash
npm run db:migrate      # 开发：migrate dev
npm run db:deploy       # 自托管运行：migrate deploy
```

**迁移文件必须入库。** 用户升级时只跑 `db:deploy`，不重新生成。

破坏性迁移（删列、改类型）必须带数据搬迁脚本，不能只写 DDL。

## 8. 备份与恢复

两种，用途不同：

| 方式 | 用途 | 说明 |
|---|---|---|
| **整目录打包** | 换机器、灾难恢复 | 停服务 → 打包 `SN_DATA_DIR` → 新机器解压。不需要协议 |
| **增量上云** | 日常备份到自己的后端 | 见 `18-BACKUP_PROTOCOL.md` |

整目录打包是**最后一道保险**，任何情况下都成立，不依赖代码是否正确。
